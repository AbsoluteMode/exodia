# Clipboard privacy markers

## Context

`ClipboardWatcher` polls the general pasteboard and stores every text, image
and file-URL change as one of the newest 50 history rows, kept across restarts
and included in encrypted backups. It never looked at the pasteboard's types.
Password managers mark the secrets they copy with the nspasteboard.org
`org.nspasteboard.ConcealedType`, and text expanders mark temporary contents
`org.nspasteboard.TransientType`. Those copies were therefore recorded in plain
SQLite rows and image files. Whytap's own Backup recovery-code copy sets both
markers and was protected only by raising `ClipboardSuppression`'s threshold.

## Decision

- `ClipboardWatcher.readSnapshot` reads the types of the pasteboard and of all
  its items first. If any item carries `ConcealedType`, `TransientType` or
  `AutoGeneratedType`, the snapshot holds only those markers; the payload is
  not read. The types are checked again after the payload is read, so a writer
  that adds its marker after its content is still excluded.
- `poll` discards a snapshot when `changeCount` moved during the read, so
  markers and payload of different writes are never combined; the next poll
  reads the newer change.
- `handleChange` advances `lastSeenChangeCount` and returns before
  classification for a marked snapshot. It logs only
  `clipboard_watcher_skipped_marked` with marker names and the change count.
  `classify` returns `nil` for any marked snapshot.
- The pasteboard itself is untouched: the user can still paste a marked copy.
- `BackupViewModel.copyRecoveryCode` is unchanged; its markers now protect it
  even without the suppression threshold.

## Rationale

The spec says transient data should not be recorded or displayed in a history.
Concealed data must at least be hidden and not stored on disk in plain text;
history rows are plain SQLite and go into backups, so not recording it is the
only option that keeps it off disk without new encryption or UI.

`AutoGeneratedType` is also skipped. The spec defines it as content an
application placed without the user copying it and expects clipboard managers
to leave it out; Maccy ignores it by default. The watcher's contract is to save
user-initiated copies. No Whytap code writes this marker.

Any marked item excludes the whole change because a pasteboard change is one
history row; recording the unmarked items would still store part of a private
copy. Reading types first keeps marked payloads out of Whytap's memory too.

## What was tested

Focused tests use temporary stores, in-memory SQLite and uniquely named
pasteboards, never the user's clipboard:

- `classify` returns nothing for concealed, transient, both and auto-generated
  text, PNG, TIFF and file-URL payloads, which still classify unmarked.
- `handleChange` writes no row and no image sidecar for every marker/payload
  combination; a marked change advances the seen change count, and the next
  ordinary copy is recorded.
- `readSnapshot` on real pasteboards returns markers without text or image
  bytes, including a marker on a later item; unmarked text, PNG and file URLs
  are recorded through the same read path.
- The actual Backup recovery-code copy, read by a watcher with its own
  suppression, records nothing; an ordinary copy afterwards is recorded.

`swift build --build-tests` passed; the focused suites passed (83 tests,
0 failures) and the full suite passed (4,295 tests, 24 skipped, 0 failures,
153 s). The installed application was not launched. The polling race guard and the late-marker check are not
exercised: a real pasteboard cannot be written deterministically between two
reads in XCTest.

## Rejected alternatives

- Store concealed copies encrypted or masked: needs a key, UI and backup
  handling for content the user can copy again from its source.
- Rely on `ClipboardSuppression` for Whytap's own copies: covers only Whytap,
  not password managers.
- Record auto-generated content: contradicts the spec's guidance and the
  watcher's user-initiated contract.
- Honor vendor-specific legacy types (for example
  `de.petermaurer.TransientPasteboardType`): outside this change; current
  password managers use the nspasteboard.org markers.

## Limits

- Rows recorded before this change stay in history and in backups already made;
  markers are not stored, so they cannot be identified retroactively.
- A writer that sets its content and marker in separate calls leaves a
  microsecond window in which a poll could read the content unmarked; the
  late-marker check narrows but cannot close it.
- Applications that do not set the markers are still recorded.
