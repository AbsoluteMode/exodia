# Current stable OpenCode 2

## Context

The app located OpenCode 1.17.12 in the user's npm installation. Its own installer
queried GitHub `releases/latest`, which still returned V1 (1.19.3) when the
new official `@opencode/cli` package already provided stable 2.1.1. Updating
through the old endpoint therefore could not reach the requested generation.

## Alternatives

- Keep GitHub V1 releases: fails the requested generation change.
- Run the upstream installer or replace the user's global npm package: changes
  terminal setup and executes installation scripts unnecessarily.
- Download the official native V2 package directly: selected.

## Decision

Explicit Install / Update app copy resolves `@opencode/cli/latest`, then the
exact matching `@opencode/cli-darwin-arm64` or `cli-darwin-x64-baseline` version.
Only stable V2 versions at least 2.1.1 are accepted. Verify the registry's SHA-512
integrity before extracting the exact `package/bin/opencode` entry to stdout.
Check the staged executable's version and atomically rename it into the existing
app-owned tool path. Local version probes are credential-free, output-bounded and time-bounded. No npm/package scripts run. Global tools and shell files
remain untouched; failures retain the previous executable.

OpenCode 2 runs with `--standalone` and the existing Process working directory;
V2 removed `--dir`. The private server inherits the child-only provider key,
isolated XDG stores and registered Case caller ancestry. Keep the supported V1
configuration shape, selected provider/model, pinned OpenRouter provider, action
policy and environment-only credential substitution. V1 1.17.12+ remains usable
while the app and its managed tool are promoted separately. Unknown major
versions and prereleases require compatibility checks.

## Rationale

A shared background OpenCode service would not inherit Whytap's per-run
credentials and could break the Case process identity chain. The official
native package distribution supplies the requested stable generation without
replacing the user's independently managed terminal executable.

## Sources

The official V2 installer resolves the npm channel and extracts its native
package. V2's migration and CLI documentation describe legacy configuration
compatibility and private standalone invocation. The checked runtime fixture
uses only a local HTTP model, disposable files and a synthetic key.

## Comments and objections

No new search provider is selected by this runtime upgrade. Search service
credentials and quotas remain a separate provider configuration decision.

## Resolution

Use current stable V2 for app-owned installs, while preserving V1 compatibility
for an orderly promotion and rollback. Promote the app before installing the
managed V2 binary; the older installed app does not understand the new version
output or standalone invocation.

## Consequences

The integration fixture checks text/tool events, selected model/provider pin,
resume history and absence of a persisted synthetic key. V2's JSON run output
can omit V1 step-cost events; the existing usage meter then reports unavailable
cost instead of inventing a zero or an estimate. Paid-provider and native Case
approval acceptance remain separate from a loopback transport check.

## Supersedes / superseded by

Supersedes the GitHub-V1 installation channel in the agent architecture. It does
not replace the feature's provider/model routing or user credentials.
